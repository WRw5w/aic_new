# 数据集统计（train / test 原生图像属性）

> 生成工具：`python tools/dataset_stats.py --split both`（只读图像文件头，不解码像素，~30s 扫完）
> 原始数据：`outputs/dataset_stats/per_image_{train,test}.csv` + `summary_{train,test}.json`
> 首次统计：2026-06-23。数据增删后重跑脚本即可刷新。

## 6. 🔑 分辨率充分性（短边 vs 候选 `--img-size`）

"放大" = 原生短边 < 目标尺寸 → 裁切区域需被插值放大（对**图像本身**造像素，区别于位置编码插值）。

| 目标尺寸 | 训练集放大比例 | **测试集放大比例** |
|---|---|---|
| 224 | 11.5% | 0.4% |
| **416** | 37.5% | **91.3%** |
| **448**（当前默认） | 42.2% | **93.7%** |
| 480 | 46.5% | 95.9% |
| **512** | 53.6% | **100.0%** |
| 576（TTA 尺度之一） | 61.5% | **100.0%** |

**由此得到的结论：**

1. **「512 输给 448」有了硬证据**：测试图长边封顶 500，所以 **512 下 100% 测试图都在被插值放大**（没有一张原生够大），448 还有 6.3% 是原生分辨率。512/576 喂进去的"高分辨率"是纯插值、无真实细节增益——这比 bake-off 当时"batch 减半 + 位置编码过度插值"的归因更本质。
2. **416 vs 448**：测试集上 416 放大 91.3%、448 放大 93.7%，差别不大，但 **416 平均放大倍数更小、插值更温和**（短边 375→416 vs 375→448）。这与"416 插值更轻"的直觉吻合（但省的是**图像**插值，不是位置编码插值）。416 仍是个合理且廉价的探针。
3. **分辨率不是提分杠杆的根因**：测试图本身只有 ~375px 短边的真实信息，448/512 都在插值放大、并不喂进更多细节；多尺度 TTA 的 576 那一档是 100% 纯上采样。这与项目反复撞到的「瓶颈 = 冻结 B/32 特征 + 不可约噪声，不是分辨率」一致。
4. **train/test 域差**：训练图巨大且脏（短边中位 483、混杂格式 / 1.9% 非 RGB / 417 张极小图），测试图小而干净（长边≤500、全 RGB JPEG）。这个域差本身值得在数据增强/分辨率策略里纳入考虑。

## 7. 复现

```bash
python tools/dataset_stats.py --split both          # train + test，文件头扫描
python tools/dataset_stats.py --pixel-stats 2000    # 附加：采样解码算通道 mean/std（对照 CLIP 归一化）
python tools/dataset_stats.py --verify              # 附加：PIL 完整性校验（更慢，可查截断）
```
